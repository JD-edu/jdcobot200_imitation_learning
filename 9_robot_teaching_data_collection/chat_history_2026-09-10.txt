======================================================================
1. 112번과 115번 코드의 부드러움 차이
======================================================================

[사용자]
여기서 112번 코드와 115번 코드가 비슷한 역할인데 로봇이 115번에서 훨씬
부드럽게 동작합니다. 이유는?

[답변 요약]
두 코드의 drive_smooth_motion()은 동일한 사인 가감속 보간식을 사용한다.

    ratio = (1.0 - cos(pi * t)) / 2.0

가장 큰 차이는 115번이 각 모터에 위치 명령을 보낸 뒤 1.5ms씩 기다린다는
점이다.

    driver.set_position(motor_id, current_target)
    time.sleep(0.0015)

6축 이동에서는 한 제어 스텝이 112번의 약 20ms에서 115번의 약 29ms로
늘어난다. 따라서 명목상 1.5초인 이동이 실제로는 약 2.2초, 명목상 1.8초인
이동은 약 2.6초가 되어 속도와 가속도가 낮아지고 더 부드럽게 보인다.

115번의 추가적인 차이:
- 캘리브레이션 오프셋 적용
- joint_limits.txt 기반 안전 가동 범위 적용
- 관절 끝단 및 기계적으로 무리가 걸리는 구간의 사용 감소

motor_control.py에는 set_speed()와 set_acceleration()이 구현되어 있지 않기
때문에 hasattr() 조건은 거짓이다. 따라서 당시 코드의 속도·가속도 설정문은
실제 부드러움에 영향을 주지 않는다.

======================================================================
2. 조그와 Waypoint 이동의 처리 함수
======================================================================

[사용자]
조그 버튼으로 3도씩 이동하는 것이나 waypoint 이동이나 동일하게
drive_smooth_motion 함수가 처리하는 것 맞죠?

[답변 요약]
맞다. 두 동작 모두 최종적으로 drive_smooth_motion()을 호출한다.

- 조그: 선택한 관절 하나를 약 0.4초 설정으로 이동
- Waypoint: 최대 6개 관절을 약 1.8초 설정으로 이동하고 0.5초 대기

115번에서는 목표 모터 하나마다 1.5ms 지연이 추가되므로, 6축 Waypoint
이동이 단일 관절 조그보다 명목 시간 대비 더 길고 부드럽게 동작한다.

======================================================================
3. 6개 모터 명령의 동시성
======================================================================

[사용자]
drive_smooth_motion은 6개의 모터를 동시적으로 명령을 내리나요?

[답변 요약]
기존 구현은 엄밀한 동시 명령이 아니다. 다음과 같이 모터 ID 순서대로 위치
명령을 전송한다.

    M1 -> 1.5ms -> M2 -> 1.5ms -> ... -> M6 -> 1.5ms -> 20ms 대기

따라서 첫 번째 모터와 여섯 번째 모터의 수신 시점에 최소 약 7.5ms의 차이가
있다. 모든 관절에 동일한 보간 ratio를 사용하므로 궤적 진행률은 같지만 실제
명령 수신 시점은 다르다.

정확한 다축 동시 명령 방법으로 다음 두 가지를 설명했다.
- Sync Write: 모든 목표 위치를 한 브로드캐스트 패킷으로 전송
- Reg Write 후 Action: 각 목표를 저장한 뒤 브로드캐스트 실행

======================================================================
4. Sync Write와 진동 개선 방향
======================================================================

[사용자]
Sync Write를 구현하면 성능이 좀 나아질까요? 현재 로봇이 커스텀 설계이다
보니 좀 진동이 있습니다.

[답변 요약]
Sync Write는 다음 문제를 개선할 수 있다.
- 관절 사이 명령 시차 감소
- 시리얼 버스 사용량 감소
- 제어 주기 변동 감소
- 하중을 공유하는 다축 관절의 협조 동작 개선

다만 Sync Write만으로 기계적 진동이 모두 해결되지는 않는다. 커스텀 로봇의
진동에는 구조물의 강성, 백래시, 공진, 하중, 모터 게인 등이 함께 영향을 준다.

권장 조합:
- Sync Write
- 실제 시각 기준 고정 제어 주기
- 충분한 이동시간
- 모터의 실제 속도·가속도 레지스터 설정
- 5차 minimum-jerk 보간

5차 보간식:

    ratio = 10*t**3 - 15*t**4 + 6*t**5

이 식은 시작과 끝에서 속도와 가속도가 모두 0이므로 유연한 링크나 백래시가
있는 구조에서 출발·정지 충격을 낮추는 데 도움이 된다.

5. 개선된 116번 코드 작성
======================================================================

[사용자]
이것을 개선한 116번 코드를 만들어 주세요.

[작업 결과]
기존 116_cobot_teaching_cali.py는 다른 용도의 파일이므로 덮어쓰지 않고
다음 파일을 새로 만들었다.

    116_robot_ui_control_sync.py

motor_control.py에는 다음 메서드를 추가했다.

    MiniFeetechDriver.set_positions_sync(positions)

Sync Write 패킷 구성:
- Broadcast ID: 0xFE
- Instruction: 0x83
- 시작 레지스터: REG_GOAL_POSITION(42)
- 서보별 데이터 길이: 2바이트
- 서보별 데이터: ID, position low byte, position high byte

116번 코드의 주요 개선 사항:
- 한 패킷으로 다축 목표 위치 전송
- 5차 minimum-jerk 궤적
- time.perf_counter()를 이용한 절대 시각 기준 20ms 스케줄링
- 복수 모션 스레드가 동시에 버스에 쓰는 것을 방지하는 Lock
- 목표 위치를 0~4095 범위로 제한
- 이동시간 조정 상수 추가

    CONTROL_PERIOD = 0.02
    MOTION_TIME_SCALE = 1.25

MOTION_TIME_SCALE 권장 조정:
- 더 빠르게: 약 1.1
- 더 부드럽게: 약 1.4~1.6

실행 방법:

    python3 116_robot_ui_control_sync.py

Python 구문 검사와 Sync Write 패킷의 주소, 길이 및 체크섬을 모의 테스트로
검증했다. 안전을 위해 실제 로봇은 자동으로 구동하지 않았다.
